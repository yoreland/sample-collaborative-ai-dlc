# Fork-local BMAD workflow seeded parallel to aidlc-v2 (v1)

This change adds a second read-only SYSTEM workflow, `bmad`, that sits beside the upstream `aidlc-v2` baseline. The platform already imports its methodology as data — nine block types composed into workflows and seeded into DynamoDB+S3 — so the BMAD 6.10.0 workshop flow is authored as a fork-local markdown dataset under `lambda/seed-blocks/bmad/core/**` (8 agents, 2 scopes, 23 stages, 20 skills, 7 templates, 3 rules, 2 knowledge docs), routed through the *same* `shared/block-mappers.js` mappers the aidlc-v2 baseline uses. The seed handler was refactored into `seedBlocks`/`seedWorkflow` helpers and now runs a second pass that writes the bmad blocks plus the `WF#SYSTEM#bmad` partition after the aidlc-v2 pass. The batch/loop runner (`run_loop.py` / KiroCrew) is deliberately not modeled, per the user's "loop 不用了".

Watch for: the RULE-id deviation is real and intentional (bmad rules ship bare layer tokens `project`/`phase-inception`/`phase-construction`, not `bmad-`-prefixed) — **confirmed** safe against collision but worth understanding (see below). BMAD's freeze/E2E checks are modeled as Rules + reviewer-gate stages rather than Sensors, which is a **confirmed** faithful-enough tradeoff given the fork has no executable sensor commands. No blocking issues found; aidlc-v2 identity, seeding, and read-only surfacing are preserved.

**Verdict**: APPROVED

## High-level view

The two datasets are built independently and never cross-feed: `buildFromFiles(files)` builds aidlc-v2 with its default workflow identity, and `buildBmadDataset(files)` calls the same `buildFromFiles` with `buildBmadWorkflow` swapped in. `buildDefaultWorkflow` was parameterized with an `options` arg that defaults to the exact aidlc-v2 identity, so calling it with no options reproduces the old workflow byte-for-byte — the aidlc-v2 non-regression rests entirely on that default, and it holds.

Collision safety is structural, not incidental. Every bmad block id is `bmad-*` kebab-case, landing in disjoint `BLOCK#SYSTEM#<type>#<id>` keys from the `aidlc-*` ids, and the two workflows live in separate `WF#SYSTEM#<id>` partitions. The one documented exception is RULE ids: the shared `mapRule` derives a rule's layer by stripping a leading `aidlc-` from the filename, so a `bmad-` prefix would yield an invalid layer. The author chose bare valid-layer tokens (`project`, `phase-inception`, `phase-construction`) that still differ from every upstream `aidlc-*` rule id and sit in the bmad workflow's own partition — a sound tradeoff that leaves the shared mapper untouched.

The workflow CRUD was intentionally not changed, and that's correct: `listWorkflows` queries GSI1 `TENANT#SYSTEM#WORKFLOW`, which both SYSTEM metas carry, so `bmad` surfaces automatically; every mutating route 403s on `tenant === SYSTEM_TENANT` regardless of id, so `bmad` is read-only for free; and `baselineScopeMembership` reads `WF#SYSTEM#aidlc-v2` placements keyed by aidlc stage ids, which bmad's `bmad-*`-keyed placements can't perturb.

The BMAD modeling tracks the source runbook closely: brownfield/greenfield are Scopes with per-stage EXECUTE membership, and the four documented divergence points (1.1 skip, 1.2 vs 1.2g, 3.8 greenfield backfill) fall out of membership rather than special-casing. Party-mode and Reviewer Gate checks become reviewer-gate/party-mode stages; the "run E2E once, last" rule becomes a single conditional operation stage. Sensors are omitted because a sensor requires a real executable command the fork lacks.

Tests assert seeded DynamoDB/S3 rows for both datasets, run every bmad block through the production `validateBlockInput`/`validateId`, prove id disjointness with aidlc-*, check the artifact DAG has no orphaned `consumes`, and verify per-scope EXECUTE membership. They exercise real behavior and would fail on revert.

### Parallel seeding wiring and the two-dataset build

The handler builds aidlc-v2 from the fetched upstream files and bmad from the bundled fork-local Map, then seeds them in sequence: aidlc blocks → aidlc workflow → bmad blocks → bmad workflow. Both go through the same `seedBlocks`/`seedWorkflow` helpers, so both honor the same insert-only guard (conditional put on `V#latest` / `META`), `dryRun`, and `reseed` semantics. `reseed`'s `clearSystemPartitions` matches `BLOCK#SYSTEM#*` and `WF#SYSTEM#*` by pk prefix, so it clears and rewrites *both* workflows in one pass — bmad is SYSTEM-owned and correctly swept, while `BLOCK#default#*`/`WF#default#*` customer forks are never matched. The `total` in the result (`blocks.length + 1 + bmadBlocks.length + 1`) counts both workflows; the reseed test's `cleared: 330` and steady `total: 120 / bmadBlocks: 95` across runs confirm both partition-sets participate.

### aidlc-v2 non-regression

`buildDefaultWorkflow(stages, rules, options = {})` merges `options` over `AIDLC_V2_WORKFLOW` (`id: 'aidlc-v2'`, name, objective, `defaultScope: 'feature'`). With no options — how the aidlc-v2 seed still calls it — the spread reproduces the original identity exactly, and the phase tree, topological placement order, rule refs, and scope refs are all still derived the same way. The test `keeps the aidlc-v2 workflow + its blocks seeded unchanged alongside bmad` asserts the `WF#SYSTEM#aidlc-v2` META, a known placement, and every fixture block are still present after bmad is seeded in the same run; the aidlc-v2 partition test still asserts the `feature`/`mvp` SCOPEREF rows. Nothing in the change touches the aidlc-v2 stage/rule data or its builder default.

### Id namespacing, collision safety, and the RULE deviation

Block identity is `BLOCK#SYSTEM#<type>#<id>`. All bmad ids are `bmad-*` (agents, scopes, stages, skills, templates, knowledge) and pass `validateId`'s kebab-case regex, so they occupy keys disjoint from the `aidlc-*` set. The test `never lets a bmad-* id collide with an aidlc-* id` computes the `<type>#<id>` sets for both datasets and asserts empty intersection, plus asserts no bmad id begins with `aidlc-` and the two workflow ids differ — this would fail immediately if a bmad file were renamed into an aidlc namespace.

The RULE deviation is the one place ids are *not* `bmad-`-prefixed, and it is sound. `mapRule` computes `base = stripMd(id).replace(/^aidlc-/, '')` and derives the layer from `base` (`org`/`team`/`project`, or `phase` for `phase-*`). A file named `bmad-project.md` would yield layer `bmad-project`, which is not in `RULE_LAYERS` and would fail validation. The author instead named them `project.md`, `phase-inception.md`, `phase-construction.md`, producing valid layers (`project`, `phase`+phase) and rule ids `project`/`phase-inception`/`phase-construction`. Those ids differ from the upstream `aidlc-project`/`aidlc-phase-*` ids, so `BLOCK#SYSTEM#RULE#project` ≠ `BLOCK#SYSTEM#RULE#aidlc-project`, and the rule refs live in the `WF#SYSTEM#bmad` partition, disjoint from aidlc-v2's. The shared mapper is left untouched, which is the right call for a fork that wants to keep taking upstream mapper updates. The tradeoff is that a rule's id no longer self-advertises its dataset; the collision test's disjointness check covers the safety property regardless.

### Read-only surfacing via unchanged workflow CRUD

`listWorkflows` issues a GSI1 query on `workflowGsi1Pk(SYSTEM_TENANT)` = `TENANT#SYSTEM#WORKFLOW`. `buildWorkflowItems` stamps that same `GSI1PK` on both workflow METAs, so a single query returns both without any CRUD change. Every mutating route (`createWorkflow`, `addPlacement`, and the rest) rejects with `403 SYSTEM workflows are read-only` whenever `tenant === SYSTEM_TENANT` — the guard is id-independent, so `bmad` is read-only by the same code that protects `aidlc-v2`.

The one place that hard-codes a single SYSTEM workflow is `baselineScopeMembership`, which reads `WF#SYSTEM#aidlc-v2` placements by `placementSk(stageId)` to default a new fork placement's scope membership. Because it keys on aidlc stage ids and bmad placements are keyed on `bmad-*` ids, the two never overlap: seeding bmad adds no `aidlc-v2`-partition rows and cannot shadow an aidlc placement lookup. Forking `bmad` itself goes through the generic `basedOn` copy path in `createWorkflow`, not this aidlc-specific helper, so bmad's own scope memberships are copied from its source partition. No single-SYSTEM-workflow assumption is broken.

### BMAD faithfulness to the runbook

The stage set maps onto the source doc's Phase 0–6 structure across the platform's four executable phases (ideation/inception/construction/operation): document-project (1.1), generate-project-context and its greenfield variant (1.2/1.2g), prd (2.1), ux (2.5), architecture (3.1), party-mode architecture review (3.3), create-epics-and-stories (3.4), backfill-project-context (3.8), the testarch family (test-design 4.1, framework 4.2, atdd, nfr, trace), the dev loop's manual inner steps (create-story, dev-story, code-review, party-mode consistency review), sprint planning/status, retrospective, and e2e-regression (5.9). The 20 skills mirror the doc's `bmad-*` command names. The excluded runbook items are exactly the loop machinery — `bmad-loop`, `bmad-build`, `run_loop.py`, KiroCrew — matching the explicit scope cut; `bmad-qa-generate-e2e-tests` is folded into the `bmad-e2e-regression` stage.

Two faithfulness judgment calls both hold up. First, sensors: the doc's byte-freeze verification, E2E-once gate, and readiness checks are deterministic checks that would ideally be SENSOR blocks, but a sensor needs a real `command` the fork can't provide, so they're modeled as Rules (`phase-construction` ATDD/freeze guardrails, `project` constitution guardrails) plus reviewer-gate stages (`reviewer` + `reviewer_max_iterations` on prd/architecture, and the party-mode review stages). Given `validateBlockInput` *requires* a command on any SENSOR, authoring empty-command sensors would fail schema validation — so Rules+reviewers is the only faithful option without inventing fake commands. Second, brownfield/greenfield: modeled as two Scopes with per-stage `scopes` frontmatter compiled into placement `scopeMembership`. The doc's "only 4 places differ" (1.1 brownfield-only, 1.2 vs 1.2g, 3.8 greenfield-only backfill) is encoded precisely: `bmad-document-project` and `bmad-generate-project-context` are brownfield-only, `bmad-generate-project-context-greenfield` and `bmad-backfill-project-context` are greenfield-only, and the rest execute under both. The e2e-regression stage carries `execution: CONDITIONAL` with a UI condition, matching "skip if no front end."

The artifact-graph modeling is faithful to the doc's most-emphasized points: `bmad-architecture` produces `component-file-ownership` (主题 25's parallel-story file-ownership table) and `persistence-design` (主题 8/9's "existing DB is a higher-tier protected asset"), and `bmad-e2e-regression`'s body captures the "each story's green is overturned by a later story, so only the final full-suite green counts" rationale.

### Schema validity and stage-graph integrity

Every non-artifact bmad block passes the same production `validateBlockInput`/`validateId` the CRUD API uses (stage mode/reviewer/number shape, scope depth enum, rule layer enum, agent tier, skill flags), and every `consumes.artifact` is produced by some stage (no orphan inputs). I separately verified every `requires_stage` value resolves to an existing bmad stage slug — the ordering edges form a real DAG, so `topologicalStageOrder` linearizes without dropping stages into the cyclic-remainder path, and gate stages land after their inputs.

### Test quality

The suite goes past existence checks. `seeds every bmad block as a SYSTEM V#latest + V#1 pair` asserts the paired rows, the GSI1 catalog key, and that bodies are externalized to S3 (bodyRef present, inline `body` undefined, S3 object equals the block body). `seeds the WF#SYSTEM#bmad workflow partition` checks the META identity (`workflowId: 'bmad'`, name, `defaultScope: 'bmad-brownfield'`, PUBLISHED, GSI1PK), the phase rows, a `PLACEMENT#bmad-prd` with a V#1 snapshot pinned to version 1, and both scope refs with snapshots. The per-scope membership test asserts brownfield-only, greenfield-only, and shared stages resolve to the correct EXECUTE maps derived from the authored `scopes` frontmatter. Each of these would fail if the seeding pass or the underlying data were reverted, because they assert the concrete rows the second pass writes. I re-ran the seed-blocks suite (22/22 green) and `npm run build -w seed-blocks` (bundle 277KB with the bmad markdown inlined) to confirm.
